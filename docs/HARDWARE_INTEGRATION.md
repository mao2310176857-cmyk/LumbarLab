# 硬件接入与自动驱动实现指南

适用对象：负责板端数据、八区位置标定和真实执行器的硬件同伴。本文对应本次交付的 Python 本地服务、16×16 ViTac 固件与执行器扩展接口；涉及新通信协议的部分均为**待双方实现的提案**，不是当前固件已经支持的功能。

## 1. 当前交付边界

| 部分 | 已有能力 | 接手方还要完成 |
| --- | --- | --- |
| 传感器输入 | JSON 串口读取、矩阵展示、校验、新鲜度检查、电脑端空载归零、记录 | 实物固件编译/烧录、串口与接线验证、稳定帧率与噪声验证 |
| 八区算法 | 个人参考、5/6/7 区接触反馈、限时动作建议、离座/失联/异常时暂停 | 实测八区索引、确认方向与单位、验证及调整阈值 |
| 执行器输出 | `ActuatorCommand`、派发去重、过期检查、输出状态与故障锁存、工厂注入入口 | 真实 adapter、板端驱动/协议/反馈、板端独立保护和验收 |
| 默认串口运行 | `DisabledActuator`，只采集及计算建议 | 明确启用已验证的真实适配器后才可能派发移动 |

当前资料不能确定电机类型、驱动板、供电、控制引脚、限位接法或实际停止状态。先取现有可运行驱动程序和接线表；没有程序时，取控制板/驱动板正反面、执行器标签、供电标签及完整接线照片，再据实定义适配。本文不分配任何电机引脚，也不指定驱动板。

原始两份 `.ino` 位于 `firmware/original/`；传感修正版是 `firmware/ViTac16x16Json/ViTac16x16Json.ino`。修正版修复了基线累加、响应点计数、帧号、全零峰值坐标及 ADC 检查类型，保留原扫描顺序。三份代码已占用 A0、D2–D8 读取压敏布；D3 按原接线同时连接移位与锁存时钟。不要将这些已占用引脚直接复用为电机输出。未在源文件中出现的引脚也需核对实物后才能分配。

本交付没有完成 AVR 编译、真实 SRAM 余量测量、烧录、台架运动或人体使用验证。自动化测试通过只证明对应软件条件，不证明实际驱动方向、停止距离或保护链有效。

## 2. 先运行软件与注入入口

在项目根目录使用 Python 3.10+。真实串口依赖必须装到**实际运行程序的同一个解释器**中；不能只在另一套 Python 里安装后认为本程序已具备串口支持。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install pyserial
.\.venv\Scripts\python.exe run.py
```

先用默认模拟验证页面、参考采集、自动建议和记录功能。安装 `pyserial` 本身不会启用真实电机。Windows 启动脚本支持透传参数；采用虚拟环境时可直接使用上面的完整解释器路径。

真实适配器的起点是 `integrations/hardware_adapter_template.py`。复制为 `integrations/hardware_adapter.py`，据硬件资料实现后，正式运行入口为：

```powershell
.\.venv\Scripts\python.exe run.py --actuator-factory integrations.hardware_adapter:create_actuator
```

等价的通用入口是 `python run.py --actuator-factory integrations.hardware_adapter:create_actuator`，前提是该 `python` 已安装串口依赖。模板也可以通过 `integrations.hardware_adapter_template:create_actuator` 加载以查看模拟行为，但模板对串口连接会故意抛出 `NotImplementedError`。它不是可用的电机驱动；不能把返回值直接改为成功来绕过。

工厂签名为 `create_actuator(source, sensor_device)`：模拟分支返回 `SimulationActuator(sensor_device)`；真实分支返回自己的适配器。现有 `AppService._connect()` 会先创建并连接 `SerialSensor`，然后调用执行器工厂。这一点决定了同 COM 方案还需要修改传感器的连接架构，不能只替换工厂。

## 3. 板端传感数据协议：当前已支持

### 3.1 串口和帧格式

默认 **2000000 baud**，一行一个 UTF-8 JSON 对象，以换行结尾。空行与 `#` 开头的诊断行被忽略；其他非 JSON 行会导致输入无效。Arduino 串口监视器应关闭，由本应用独占所选 COM。

2Mbaud 并非所有 USB 串口设备或驱动都支持；能选择该数值不代表连接已稳定，需要实际确认。速率能力与写超时接口可参阅 [pySerial 官方 API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html)。

| 字段 | 必需 | 当前主机要求 |
| --- | --- | --- |
| `seq` | 是 | uint32 整数，0..4294967295 |
| `t` | 是 | 板端 `millis()`，uint32 整数；不是电脑端时间 |
| `base` | 是 | 整数 0 或 1；0 表示未完成板端空载基线，不能参与控制 |
| `diff` | 是 | 长度恰好 256 的数组；每项为 0..255 整数 |
| `raw` | 否，但建议始终提供 | 长度恰好 256，同样为 0..255 整数；电脑端归零必须有它 |
| `peak` | 否 | 最大响应，0..255 |
| `pr` / `pc` | 否 | 峰值行/列，-1..15；没有响应时都应为 -1 |
| `nz` | 否 | 非零响应点数，0..256 |
| `sum` | 否 | 全阵列相对响应总和，0..65280；不是已标定的力 |

统计字段如提供会检查类型和范围；八区计算使用数组，不依赖这些统计值。布尔值、浮点值或 `NaN` 不能充当上述整数。每行最多 8192 字节，过长行被丢弃到下一个换行后恢复。

以下 Python 代码可直接运行，生成**一行完整且通过当前 `parse_frame` 校验的 JSON**，没有省略数组元素。它是协议样例数据，不是真实测量数据：

```python
import json
from lumbar.devices import parse_frame

raw = [12] * 256
diff = [0] * 256
row, column = 5, 6
index = row * 16 + column
raw[index] = 42
diff[index] = 30
frame = {
    "seq": 1,
    "t": 1000,
    "base": 1,
    "peak": 30,
    "pr": row,
    "pc": column,
    "nz": 1,
    "sum": 30,
    "diff": diff,
    "raw": raw,
}
line = json.dumps(frame, separators=(",", ":"), allow_nan=False)
assert len(parse_frame(line)["diff"]) == 256
assert len(parse_frame(line)["raw"]) == 256
print(line)
```

若需要降低波特率，须同时修改板端 `BAUD_RATE` 并重新烧录，以及网页中的波特率选择。当前服务允许 115200、230400、460800、921600、1000000、2000000；其他速率需同步修改 `AppService._connect()` 的允许值和网页选项。降低速率后应实测带宽与帧间隔，必要时降采样/降低输出频率，不能只改一端。不要为了省带宽关闭 `raw` 后又使用电脑端归零。

### 3.2 帧新鲜度与记录边界

主机对收到的完整帧使用自己的单调时钟记到达时间；设备 `t` 用于顺序检查，不作为主机新鲜度时钟。重复帧和倒序帧不刷新数据时间，uint32 正常回绕允许，可能重启会清除电脑端基线并要求重新连接。没有 boot id 时，早期旧包与重启不能完全区分。

`SerialSensor.read()` 每次交付最近一帧，且同一帧只交付一次；主循环约每 50 ms 读取。这是最新状态接口，**不是逐帧无损采集队列**：串口帧率高于消费速率时，中间帧可能被覆盖。实验记录保存主循环消费到的帧及异常状态；若需要逐帧无损保存，须另外实现有界采集队列/独立落盘，并监测溢出。

## 4. 16×16 索引与八区映射

索引规则是 `index = row * 16 + column`，行、列都从 0 到 15。索引 0 是扫描数组 `(0,0)`，255 是 `(15,15)`；它们不自动代表人体左/右、座面前/后。应以坐在椅子上的使用者为左右参照，逐区施加已知小面积载荷，记录方向和实际索引。

| 分区键 | 当前界面/算法含义 |
| --- | --- |
| `1` | 左前座 |
| `2` | 右前座 |
| `3` | 左后座 |
| `4` | 右后座 |
| `5` | 左腰 |
| `6` | 中腰 |
| `7` | 右腰 |
| `8` | 上背 |

修改 `config/zones.json`，键必须恰好为字符串 `"1"` 到 `"8"`，值为对应像素的索引列表。必须全部八区非空，索引是 0..255 整数，同一区及不同区之间都禁止重复。允许有未分配像素。分区值取所列像素的**均值**，单位仍为 0..255 相对读数。不要把面积更大的区直接改为求和而继续使用现有阈值。

出厂文件八区全空是有意保留的待标定状态。全部为空或部分为空时，`map_zones()` 返回 `None`，主机不能记住个人参考或开启自动；矩阵本身仍可用于观察。不要用随意切成八块的假映射来解除门槛。文件更改后重新连接，让服务创建新的 `SerialSensor` 并读取映射。

当前一个输入帧必须同时包含八区的数据。**如果实际只有腰部一块布，根本没有座面和上背传感器，则现有八区模型无法直接成立。** 应补齐真实采集、约定多板数据聚合，或者明确修改状态模型、入座判断、参考条件和界面；不能复制腰部像素填充座面/上背，也不能填常数假装有人入座。

## 5. 三种不同操作：板端基线、电脑归零、个人支撑参考

| 操作 | 前提与作用 | 会不会发送电机动作 |
| --- | --- | --- |
| 板端空载基线 | 原传感固件启动时自动采 16 帧；调试命令 `b` 也会重采；必须布面无人无物 | 原固件没有电机驱动 |
| 网页电脑端归零 | 用户确认空载；主机对最近 raw 窗口求均值，后续用 `max(raw - host_baseline, 0)` | 先请求执行器停止；不会向传感器发送 `b` |
| 记住当前支撑 | 使用者坐好，将支撑调到合适位置后稳定采集约 3 秒；至少 20 个有效样本并通过接触/波动检查 | 采集时停止移动，采完等待明确开启自动 |

串口打开可能令 Nano 自动复位，从而触发板端自动基线。连接、上电或烧录后的启动阶段均需空载。若合并电机控制，应重新设计明确的启动/空载校准流程，不能有人使用时因 USB 重连就静默把受力姿态当作空载。

电脑归零要求最近 raw 不超过 0.5 秒，最近 1 秒至少 5 帧、跨度至少 0.5 秒，每像素最大值与最小值之差不超过 20，且采集帧 `base=1`。归零后必须继续提供 raw；缺 raw 就失效，不切回另一套基线。归零成功会清除个人参考，需重新记住支撑；断开、重新连接或检测到板端重启也会丢弃电脑端基线。

`raw_zones` 是原始 raw 的区均值，`zones` 是扣除当前基线后的区均值。不能把 0..255 直接称为牛顿、公斤或已标定压力。个人参考表示用户这次认可的接触分布，不是自动推断的“正确坐姿”或医学舒适标准。

## 6. 选一种通信拓扑

### A. 传感器和执行器使用不同 COM

可以保留现有 `SerialSensor`：它独占传感 COM，接收当前传感 JSON，保持只读。电机 adapter 自己持有**另一个**执行器 COM，管理命令、ACK、FAULT 和可选状态反馈。执行器端口/波特率通过 adapter 自己的配置确定，不能照抄 `sensor_device.port`。

执行器 COM 也应只有一个接收线程。`execute()` 可提交命令并以有界超时等待该接收线程匹配的 ACK；不要让 `execute()` 和后台线程同时读同一串口。程序退出/重连时先处理停止，再释放执行器端口；还要处理同一个执行器 COM 重建连接时旧对象仍持有端口的生命周期问题：当前 `_connect()` 在新工厂创建成功后才关闭旧 adapter。若新旧 adapter 要打开同一个执行器 COM，应调整为旧执行器确认停止、释放旧连接后再构造新实例；失败后保持暂停，不恢复旧动作。明确传感器与电机各自资源所有权，`close()` 应可重复调用。

### B. 同一 Nano、同一个 COM 同时传传感数据和电机消息

**必须共享一个串口对象及一个读线程。不能让 `SerialSensor` 和电机 adapter 各自 `serial.Serial(...)` 打开同一个 COM；也不能让两个消费者竞争 `read()`。**

建议新增 `SharedSerialTransport`（待实现）：负责独占打开/关闭、单读线程、完整行解析、消息类型路由、有界缓冲和串行化写入。传感器视图消费 sensor 队列，执行器 adapter 消费 ACK/FAULT/STATUS 队列；等待 ACK 时由共同读线程继续接收，不占用第二个读循环。

消息路由采用 `type` 字段，例如 `sensor`、`ack`、`fault`、`status`。这是新的双向协议提案。当前纯传感 JSON 没有 `type`；平铺增加 `type:"sensor"` 且保留原必需字段可以继续满足传感字段校验，但仍须先做路由。当前 `parse_frame()` 不负责路由，ACK/FAULT 直接混入传感流会因为缺少 `seq/t/base/diff` 等被判无效；不能简单在 ACK 前加 `#` 后扔掉，它会丢失执行确认。

同 COM 方案至少要改：

- `lumbar/devices.py`：`SerialSensor.__init__/connect/_reader/close` 改为使用共享 transport、正确分配所有权；`_process_line()` 只处理已路由的传感帧；需要时将 `parse_frame()` 拆成行解码与传感负载校验两层。保留 `read()` 返回最新 `SensorFrame` 的约定及原有新鲜度检查。
- `lumbar/service.py`：`_connect()` 构造共享 transport 并传给传感器视图及 adapter；处理连接失败、停止后关闭和重连时的资源释放。只改 `actuator_factory` 不能完成这一步。
- 板端：替换当前 `handleCommands()` 的逐字符调试解析，新增有界、非阻塞的逐行命令解析和结构化 ACK/FAULT 输出；发送端保持行不交错。

**不要把下节的 JSON 命令直接发给现有 `.ino`。** 现有固件按字符处理 `b/j/r/t/h` 等调试命令，JSON 内的这些字母可能被误解释为重新校准或切换输出。必须先完成板端解析器改造，或者使用独立执行器 COM。

## 7. 实现 Python 执行器 adapter

### 7.1 已存在的调用契约

执行路径：`Controller` → `AppService._dispatch_control()` → `ActuatorDispatcher` → `adapter.execute(command)`。

`ActuatorCommand` 只有以下字段：

| 字段 | 含义 |
| --- | --- |
| `action` | `advance`、`retract`、`hold`、`stop` |
| `issued_at` | 电脑端单调时钟签发时刻，秒 |
| `speed` | 当前模型中的模拟行程百分比/秒；范围 0..10，移动必须大于 0 |
| `duration_s` | 移动的有界持续时间，必须大于 0 且不超过 2 秒；hold/stop 为 0 |
| `expires_at` | 计算属性 `issued_at + duration_s`，属于电脑端时钟 |

**传给 `execute()` 的 command 没有 `seq`。** 页面 `state.actuator.command.seq` 是 `ActuatorDispatcher` 为展示/记录加的序号，不随 `ActuatorCommand` 进入 adapter，也不能假设跨连接唯一。wire 协议的 `session` 与 `command_id` 必须由 adapter 自己生成、保存并用于确认/去重。

真实 adapter 声明 `enabled=True`、`is_hardware=True`，实现 `execute(command) -> ActuatorResult`，并建议实现 `close()`。只有真实完成初始化、协议握手与输出状态检查后，才能声明可用；不是把标志改为 True 就算驱动接通。

`ActuatorResult(sent, acknowledged, message)` 的含义须诚实：写入发送缓冲不等于板端已接收；没有匹配 ACK 不能返回 `acknowledged=True`。当前服务在 enabled 适配器返回未发送或未确认、或抛异常时会锁存执行器故障，暂停并尝试停止。因此 execute 需要在有限时间内获得匹配确认，或明确失败；无限等待会拖住控制主循环及用户操作。

这是**同步 ACK 契约**：不能先返回 `sent=True, acknowledged=False` 表示“处理中”，因为当前服务会立即把它当作故障。需要异步派发时，必须同时重构服务的待确认状态、超时和停止路径。当前 execute 在服务的 `RLock` 内调用，长时间等待会延迟网页请求和暂停操作。pySerial 的 `write()` 默认可阻塞；实际 adapter 应显式设置 `write_timeout`，并给 ACK 等待设定经台架验证的短上限。即便主机卡住，板端仍必须按自己的时限停止。

现有同一次运动会复用签发时刻/时限；主循环不会通过重复 tick 延长它。通常自动动作单次上限 0.8 秒，手动一小步为 `2/speed` 秒。适配器须据实将速度意图映射到已标定的驱动单位，不能把数值 5 直接当作 PWM 占空比、电压或毫米/秒。

### 7.2 时限、ACK 和异步故障

- `issued_at/expires_at` 来自电脑时钟，**不能直接传给 Nano 当作其 `millis()` 时刻**。发送前重新计算剩余时间；已过期直接拒绝移动并请求停止。使用剩余毫秒时须扣除经过验证的传输/排队延迟余量，板端另有硬时限；板端从接收时计时会额外加入在途延迟，不能宣称等价于主机绝对截止时间。若无法保证延迟上界，须设计时钟/租约同步或拒绝该过短动作，不能忽略此问题。
- ACK 应说明“已接受/已拒绝该命令”，并匹配 session、command_id。**收到执行 ACK 不表示运动完成、已经到位或物理停止已测得。** 完成/限位/实际状态应有独立 STATUS/DONE/FAULT 反馈；stop 的 ACK 也必须清楚表示是已接受停止请求还是已经验证停止输出。
- 当前 `AppService` 没有通用 `poll_status()` 或异步 FAULT 输入钩子。仅在 adapter 线程里记录一个错误不会自动改变主机状态。接手方须增加有界状态/故障队列或共享故障快照，在 `tick()` 中主动轮询并联入 `actuator_fault`、`controller.pause()`、停止请求、事件记录和界面；不要等到下一次 execute 才发现故障。
- 当前真实模式 `position=None`；仅加 adapter 不会让网页显示真实行程。若有编码器/位置反馈，须定义单位、新鲜度、范围与可信状态，并修改 `AppService.tick()` 传给控制器的 position 及 `_state()`。当前 `Controller.update()` 的 position 边界使用 0.1/99.9 的模拟百分比：不能直接传入毫米或编码器计数；须先按已标定行程转换到对应归一化范围，或同时重写该边界逻辑并明确记录原物理单位。主机行程判断不能代替板端硬限位。
- `hold/stop` 会被派发器去重；同一次运动也不会重复派发。**不能把 execute 调用、保持命令或持续收到 sensor 数据当作主机心跳。** 若需心跳，须独立设计与主机健康状态挂钩的机制；自动后台线程不能在主控制循环已失效时持续“代报健康”。

## 8. MCU 自动驱动逻辑与协议提案

### 8.1 板端先实现这些行为

1. 启动和复位进入明确安全输出状态，禁止恢复上次未完成移动；必须完成新 session 握手、硬件自检及使能条件后才接收移动。
2. 使用非阻塞状态机，例如 `IDLE / ADVANCING / RETRACTING / FAULT`，按实际驱动定义引脚和电气安全状态。传感扫描、串口收发、动作截止、限位、急停都须及时得到处理。
3. 每次移动有板端自己的硬时限，收到的时长还要被板端限幅；到期无条件结束当前动作。使用能正确处理 `millis()` 回绕的比较方法。
4. **stop 和 hold 都必须终止旧的移动状态。** hold 不能被实现为“不处理该包，继续上次前顶”；是否断能、制动或保压依据驱动结构另行定义并验证。更换方向必须先结束旧动作，遵守驱动所需的换向间隔。
5. 限位、急停、允许行程、最大驱动力/压力、过流/堵转等按实际硬件可用反馈在板端实施；不能依靠 PC 页面是否仍在线。断连/命令租约过期须独立停机，故障锁存后需明确的安全恢复过程。
6. 有界解析输入，禁止畸形包或超长包使主循环阻塞；只接受允许状态下的有效命令。stop 不应排在长运动命令队列后等待执行。
7. 传感代码中的整帧扫描、16 帧基线采样、`delay()` 及大量 `Serial.print()` 都可能占用执行时间。合并驱动时须拆为可推进的小步骤或证明最坏处理延迟；特别是校准期间也必须响应停止、急停和截止。不能仅给原 `loop()` 追加 motor 代码就认为具备实时保护。

### 8.2 一个需要共同实现的协议草案

以下是说明字段的**提案示例**，不是本次交付已经能执行的串口命令，也不是建议现在发送的测试指令：

```json
{"type":"command","session":"bench-session-001","command_id":7,"action":"advance","speed_request":5.0,"remaining_ms":300}
```

```json
{"type":"ack","session":"bench-session-001","command_id":7,"accepted":true,"status":"accepted"}
```

```json
{"type":"fault","session":"bench-session-001","code":"LIMIT_REACHED","motion":"stopped"}
```

字段单位、最大长度、拒绝原因、状态含义、握手、心跳、复位身份和重传策略需在主机与 MCU 两端共同落地。`speed_request` 只是主机意图值，具体驱动输出仍要标定；`remaining_ms` 需按上一节的延迟和板端硬限处理。

同一 session 内使用单调 command_id。ACK 丢失后如允许重传，必须重发同一个身份，而不能生成新 id 来续动作；MCU 应记住该 id 已接受、已结束、已取消或已拒绝的状态。重复包仅重发原结果，不能重启电机或重置截止。被 stop/hold/反向命令替代的旧包、乱序包和过期重传都不能复活动作。新 session 不应自动获得运动权限；MCU 复位也要使旧 session 无效。若采用有限缓存，应配合最高已处理 id/会话策略，不能让被淘汰的旧命令再次当成新命令执行。

## 9. 算法能力与当前未实测阈值

当前控制的是一个前后方向自由度：5、6、7 区的平均相对接触量与个人参考比较，并对局部偏强做约束。**一个腰托不能独立调节左、中、右三点**；左强右弱可能需要用户调整或机构改变，不保证一次整体前顶/回退能同时修正三点。若改成三执行器，需要重新设计动作模型与耦合控制，不能直接复用一个 action 给三路。

当前入座条件为 1–4 区均值至少 5；腰部接触条件为 5–7 区均值至少 3；参考采集要求每个腰区均值至少 8，并拒绝接近 240 的参考；运行中任一腰区值达到 245 触发停止。这里的 245 检查的是**扣基线后该腰区的像素均值**，不是原始 raw ADC、单个像素峰值或力值；不能把它当作原始 ADC 饱和检测或物理压力限制。数据超过 0.8 秒未更新会暂停。默认容差 18%、偏差持续 0.6 秒、动作后等待 0.6 秒；参考带宽还考虑噪声。

这些是软件原型参数，**尚未由这套实物传感器、供电、布料、机构和人群验证**。相对 ADC 接近上限不是已标定的安全力上限。调参不能替代板端物理保护，也不能根据这套数值推断脊柱形态、疼痛风险或医疗效果。

网页中的“有点顶／支撑合适／有点空”三个反馈按钮仅向正在记录的实验写入事件，不训练模型，不自动修改阈值或个人参考。

### 9.1 与源码对应的控制规则

记 `T` 为参考 5/6/7 均值，`L` 为当前滤波后 5/6/7 均值，`local` 为三个腰区各自除以其参考值后的最大比值，`tol` 为容差。三处反馈用于同一整体动作。

| 项目 | 当前源码行为 |
| --- | --- |
| 滤波 | 仅新消费帧更新：`filtered = 0.3 * new + 0.7 * previous`，按帧而非固定物理时间常数 |
| 参考带半宽 `M` | `max(T * tol, mean(reference_noise[4:7]) * 3, 3)` |
| 保持参考区间 | `[T - M, T + M]` |
| 开始回退候选 | `L > T + M` 或 `local > 1 + 1.5 * tol` |
| 开始前顶候选 | `L < T - M` 且 `local <= 1 + 0.6 * tol` |
| 前顶结束 | `L/T >= 1 - 0.4 * tol` 或 `local > 1 + tol` 或动作到期 |
| 回退结束 | `L/T <= 1 + 0.4 * tol` 且 `local <= 1 + 0.6 * tol`，或动作到期 |
| 候选确认 | 同方向偏差持续 `persistence_s`，且有新输入，才启动动作 |
| 自动动作上限 | 单段 0.8 秒；到期/达到停止阈值后进入停稳阶段 |
| 手动动作上限 | `2/speed` 秒，默认 0.4 秒；连续点动和换向共享原期限 |
| 默认参数 | `tolerance=0.18`，`persistence_s=0.6`，`settle_s=0.6`，`speed=5.0` |
| 当前可调范围 | 容差 0.08–0.4，偏差持续/停稳 0.2–3 秒，模拟速度 1–10 |

优先检查无效、超时、离座、腰部接触丢失及上述高信号条件，再执行反馈逻辑。短暂偏差不动作；整体偏弱但局部过强时可能保持，避免来回拉扯。反馈方向假设是“前顶增加接触、回退减小接触”，需要对实际机构验证。参数更改会暂停，需明确重新开启自动。

## 11. 验收顺序：无人台架 → 数据 → 闭环

### 第一步：无人台架验证真实驱动

- 网页手动按钮也要求有效八区、在座、腰部接触且未达上述量程门槛，**不能在空载台架上直接靠网页点动电机**。先用硬件方独立的台架固件/工具验证驱动，不要删除主应用的信号保护，也不要伪造有人入座的数值绕过。
- 先确认上电/复位默认输出和独立急停；再验证停止/保持确实结束旧动作，确认前顶与回退方向。
- 使用已核实的电气参数与小幅有界动作，测量时限、停止延迟/距离、行程边界与故障状态；不在人体接触时首次测试。
- 模拟拔线、杀掉 PC 进程、PC 控制循环卡住、ACK 丢失、串口堵塞、MCU 复位、重复与旧命令重放。板端应独立结束动作，重连不能恢复旧动作。
- 区分“命令已接收”“输出已停”“机械已停/到位”各自证据，记录最坏延迟与哪些状态无法测得。

### 第二步：验证真实数据及八区

- 在不启用真实驱动的模式下连接传感器；确认 2Mbaud 或双方约定的速率、连续有效 JSON、raw/diff 范围和稳定帧率。
- 空载完成基线与电脑归零；逐区施加已知载荷，确认 16×16 朝向、八区位置及左右一致，未触碰区域不被复制或伪造。
- 检查 base=0、畸形数据、超长行、重复/倒序、断流超过 0.8 秒和重启的界面/记录表现。若使用同 COM，ACK/FAULT 必须经过正确路由，不污染 sensor 输入。
- 验证记录包含原始数据与事件，并理解当前最新帧记录不是无损采集。实测噪声后才评估参考条件和阈值是否合理。

### 第三步：先建议，后有界闭环

- 先保持真实驱动禁用，检查个人参考与偏轻/偏强建议方向是否符合机构和数据变化；确认离座/接触丢失会暂停，恢复数据不会自行重新开启。
- 台架保护通过后启用已实现的 adapter，先手动有界动作，再在可控负载下测试自动：动作改变接触量，进入参考带后停止，动作后等待稳定，无持续追赶或来回振荡。
- 核验当前输出状态、匹配 ACK、独立运动结束/故障反馈和真实位置（如果提供），而不是只看页面 action。
- 完成以上记录并确定实物限制后，才安排有人接触的低强度使用评估。接手验收应注明日期、软件/固件版本、硬件配置、参数、通过项、失败项和未测项。

交付完成判据是：真实传感、真实分区、真实驱动与独立保护都有可追溯的实测结果；单纯插上串口、页面有数值或收到 ACK，均不足以认定整机自动支撑功能已经完成。
